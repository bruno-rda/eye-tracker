# Live and replay share one pipeline that takes time only from the stream

A source yields frames and events in arrival order, each stamped at capture on one clock; perception, estimator and controller run as synchronous steps on one thread and never read a clock, the camera or the OS. Live and replay then differ only in the adapters at the two ends (camera or recorded session, macOS cursor or a log), so replay scores the code that runs live, and settling windows and trackpad stillness are deterministic. The cost: a frame arrives after its exposure (delay unmeasured), so stages must tolerate a frame older than the last event, and a slow stage shows as backlog, never as dropped frames. Sorting by timestamp was rejected: live cannot do it without waiting. Separate replay code was rejected: it would score something other than what moves the cursor.
